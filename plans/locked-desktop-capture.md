# Locked-desktop capture: ranked implementation plan

## 1. Default: keep the proven in-process RT path
- **Use the mirror's proven offscreen renderer + `ReadPixels`, not desktop capture.** Locking switches the visible desktop; it does not inherently prohibit the game's D3D device from rendering an owned RT. This should work while locked **if the player loop and graphics device remain operational**; it is not a Unity guarantee for every driver/window state.
- `Application.runInBackground = true` permits background ticking, not guaranteed rendering or progress through an occluded `Present`. Presentation may be skipped/throttled while RT commands still work; a blocked main/render thread, device removal, sleep, or disconnected-session device reset can stop both. Logs alone do not prove animation/render progress. [U1]
- Re-assert `runInBackground` on focus/pause changes and periodically from the main thread. Queue requests using monotonic `Stopwatch`/`Time.realtimeSinceStartupAsDouble` deadlines; consume in a main-thread `LateUpdate`, outside any camera render. A worker timer may enqueue only: **never call Unity APIs from it**. Coalesce overdue requests, do not catch up in a burst.
- Do not schedule by frame counts, scaled `WaitForSeconds`, or depend exclusively on `WaitForEndOfFrame`/render callbacks, which may stop arriving. `Time.deltaTime` is scaled/clamped by `Time.maximumDeltaTime`; a wall-clock deadline neither advances an Animator nor guarantees its pose. Record realtime, frame number, Animator state/normalized time, and capture result; require distinct poses for emote evidence.
- For the verification actor only, temporarily use `Animator.cullingMode = AnimatorCullingMode.AlwaysAnimate` and, if necessary, `SkinnedMeshRenderer.updateWhenOffscreen = true`; restore afterward. Offscreen visibility culling can freeze bones even while `Update` logs continue. Keep simulation time unchanged unless an isolated deterministic-pose test is explicitly intended.
- Lock does **not** imply a mandatory process-priority change. Windows visibility/QoS heuristics, Efficiency mode, driver background-FPS limits, and power policy can reduce throughput. Inspect those if deadlines slip; optionally disable execution-speed throttling with `SetProcessInformation(ProcessPowerThrottling, PROCESS_POWER_THROTTLING_STATE)` (`ControlMask = PROCESS_POWER_THROTTLING_EXECUTION_SPEED`, `StateMask = 0`), retain Normal priority, and adjust a verified driver/background cap. No Realtime priority or global power-policy changes by default. [W1]
- **URP correction:** preserve the empirically working `Camera.Render()` adapter; do not claim it universally fails in SRP. Unity 6.3's prescribed URP route is `UniversalRenderPipeline.SingleCameraRequest { destination = rt }`, `RenderPipeline.SupportsRenderRequest(cam, request)`, then `RenderPipeline.SubmitRenderRequest(cam, request)` (synchronous). Prefer that as the compatibility fallback, not an untested replacement of the working mirror path. Never render a camera recursively. [U2,U3]

## 2. Alternatives, ranked by usefulness while locked
| Rank | Exact mechanism | Decision / decisive caveat |
|---|---|---|
| 1 | Dedicated disabled `Camera`; copy viewpoint with `Camera.CopyFrom` + transform; `SingleCameraRequest` → owned RT | Best fallback if the mirror camera's manual-render path fails or its framing is unsuitable. Copy/configure URP additional camera data, renderer choice, layers, postprocessing and aspect separately; `CopyFrom` does not reproduce every URP component/stack. Use `RenderPipeline.StandardRequest` on a Base camera only when the whole stack is required. [U2,U3] |
| 2 | Enabled second camera with `Camera.targetTexture = rt`, or temporarily swap the live Base camera's `targetTexture` | Lets the normal URP render loop produce RT content. Read only after the selected camera completes (`RenderPipelineManager.endCameraRendering`, or end-context for a stack). Save/restore target in `finally`; avoid the live-camera swap unless necessary. **Fails if that render loop is suspended**, so weaker than an explicit render request. |
| 3 | `AsyncGPUReadback.Request(rt, 0, TextureFormat.RGBA32, callback)` | Optimization for stalls, **not another image source or a cure for stalled rendering**. Require `SystemInfo.supportsAsyncGPUReadback`, compatible format, `!request.hasError`; retain RT until completion, one request in flight, copy callback data before expiry. Fall back to synchronous `ReadPixels` on supported-device/readback errors. Native delegate lifetime/interop adds IL2CPP complexity. [U4] |
| 4 | In-process swap-chain hook (e.g. OBS **Game Capture**, D3D11 texture copy before `IDXGISwapChain::Present`) | May work independently of DWM if the game keeps producing/hooking frames; can include final UI. Not guaranteed if `Present`/normal rendering stops; injection/hook compatibility and native crash risk make it a last resort, not a first fix. [O1] |
| Reject | `PrintWindow(hwnd, memoryDC, PW_RENDERFULLCONTENT /* 0x2 */)` | Not a reliable Unity/DX locked-session fallback. Cooperative `WM_PRINT` drawing can work for some windows even on an inactive desktop; there is no universal “requires unlocked” rule. But flag 0x2 does not force Unity to redraw its GPU swap chain. With DWM content unavailable/suspended, expect black/stale/partial output unless the app supplies it. Return success does not prove fresh pixels; the call can block. Do not spend effort on this path. Lock also does not necessarily suspend DWM globally. [W2] |
| Reject | `IDXGIOutput1::DuplicateOutput` → `AcquireNextFrame` (DXGI Desktop Duplication) | **Dead end for the hidden game's frames while locked**: desktop switch invalidates duplication (`DXGI_ERROR_ACCESS_LOST`); secure-desktop access can fail `E_ACCESSDENIED`; non-DWM mode is unsupported. Recreate after unlock. SYSTEM access to the active secure desktop would capture that desktop, not the hidden game. [W3] |
| Reject | WGC: `IGraphicsCaptureItemInterop::CreateForWindow`, `Direct3D11CaptureFramePool`, `GraphicsCaptureSession.StartCapture()` | No supported guarantee of fresh hidden-window frames across lock; frame delivery may cease/freeze. WGC handles occluded windows in ordinary sessions, but that is not a locked-session contract. **Treat as a dead end for reliable locked verification**, not as a universal assertion that every Windows build always fails. [W4] |
| Reject | NVIDIA NvFBC (`NvFBCToSys`/`NvFBCToDX9Vid`), ShadowPlay desktop mode | Framebuffer/desktop capture does not recover the hidden game from a switched desktop. NvFBC Windows 10+ is deprecated; hardware/API access restrictions add cost. ShadowPlay game-hook mode is at best rank 4, not a lock bypass. [N1] |
| Reject | OBS Virtual Camera; FFmpeg `-f gdigrab -i desktop` / `-f gdigrab -i title=...`; `-f lavfi -i ddagrab` | Virtual Camera only republishes an OBS source; it captures nothing itself. `gdigrab` inherits GDI/window-capture limitations; `ddagrab` inherits Desktop Duplication's locked-desktop failure. Only feeding OBS an already-working in-process source changes the result. [O1,F1] |
| Reject by default | Backbuffer `ReadPixels` with `RenderTexture.active = null`; `ScreenCapture.CaptureScreenshotIntoRenderTexture` | Needs a valid, completed normal screen frame at the correct render phase; backbuffer lifetime/UI composition depends on graphics API and URP. Neither reliably forces a frame while occluded, and ScreenCapture shares the suspect subsystem. A URP renderer pass copying camera color to an owned RT is safer than native backbuffer access, but still depends on normal pipeline execution. |

## 3. UI: pay only when required
- **For hats/emotes, accept no UI.** World-space canvases and camera-space uGUI can already appear if the capture camera renders their layers; **Screen Space - Overlay uGUI and IMGUI are not included by simply re-rendering a scene camera**.
- Cheapest reliable mod UI: a small capture-only uGUI canvas (`renderMode = RenderMode.ScreenSpaceCamera`, `worldCamera = captureCamera`, valid `planeDistance`, matching sorting/layers), populated from the same state as the buttons. `Canvas.ForceUpdateCanvases()` before rendering. Alternatively use a UI camera in a supported URP stack and `StandardRequest`; a single-camera request omits the other stack cameras. [U3,U5]
- For existing game HUD uGUI, temporarily switch each relevant root Overlay canvas to `ScreenSpaceCamera`, assign the capture/UI camera, and force layout. Save/restore `renderMode`, `worldCamera`, `planeDistance` and any changed sorting/scaler state in `finally`; camera viewport/aspect/layout can change. Clone only if its bindings/lifecycle are understood; do not blindly clone the entire HUD.
- IMGUI (`OnGUI`) does not become camera-space by switching a Canvas. Reproduce the small required mod overlay in capture-only uGUI or composite a separately rendered annotation; label it reconstructed, not literal HUD evidence. Exact arbitrary IMGUI/final-HUD evidence needs a functioning final-frame path (rank 4 or an unlocked test), not another `Camera.Render()`.

## 4. Crash safety and exact recommended routine
- Prior `ScreenCapture.CaptureScreenshot` deaths establish correlation, not cause. Candidates: native screenshot/driver fault, invalid final-frame state during lock/resize, supersize/repeated allocations causing OOM, wrong-thread/reentrant invocation, or missing/incorrect IL2CPP generated binding/internal-call resolution. A missing managed binding may merely throw; do not diagnose a native crash without Player.log plus a crash dump/native stack. [U6]
- RT capture is **safer here because this exact render/readback/encoder path is proven**, uses owned fixed-size resources and avoids screen/backbuffer acquisition. It still uses native Unity/driver code and synchronous GPU work: neither `catch` nor BepInEx can contain an access violation, device hang or process termination.
- Implement **one bounded, non-reentrant main-thread routine**, with a selectable render adapter (proven `Camera.Render` first; URP request after compatibility testing). Suggested exact sequence:
  1. Enqueue one request with monotonic due time, absolute destination and pose metadata; cap at one pending request, one in flight, ≤1 capture/second and a finite per-test count. Drop excess. No per-frame PNG loop.
  2. Consume after animation/bone attachment updates in a controlled `LateUpdate`; defer if another camera/capture is rendering. If aiming at a mirror, update its RT first, then render the view containing it; prevent capture-camera recursion in mirror callbacks.
  3. Under the outer exception guard, validate live camera/actor, dimensions and path; set `runInBackground = true`. Allocate/reuse **owned** 1280×720 `new RenderTexture(1280,720,24,RenderTextureFormat.ARGB32)`, MSAA 1, no mipmaps, and readable `new Texture2D(1280,720,TextureFormat.RGBA32,false)`. Call `rt.Create()` and verify `rt.IsCreated()`; recreate lost RTs once, not every tick.
  4. Save `oldActive = RenderTexture.active` and `oldTarget = cam.targetTexture`; enter an inner `try/finally` before changing either. Configure an idle dedicated camera or borrow the proven idle mirror camera, preserving any modified settings.
  5. Proven adapter: `cam.targetTexture = rt; cam.Render();`. URP fallback adapter instead: construct `SingleCameraRequest { destination = rt }`; reject if `!RenderPipeline.SupportsRenderRequest(cam, request)`; call `RenderPipeline.SubmitRenderRequest(cam, request)`. Do not issue both renders for one capture.
  6. After render completion: `RenderTexture.active = rt; pixels.ReadPixels(new Rect(0,0,w,h), 0, 0, false);`. Keep the CPU texture readable. `Apply()` is unnecessary for CPU-only PNG encoding; if retained for binding compatibility, use `Apply(false, false)`, never discard CPU pixels. [U7]
  7. In the inner `finally`, restore `RenderTexture.active = oldActive` and `cam.targetTexture = oldTarget` plus borrowed settings. Attempt each restoration even if another cleanup operation fails; guard destroyed Unity objects. Never release/destroy a borrowed mirror RT.
  8. `png = ImageConversion.EncodeToPNG(pixels)`; reject null/empty bytes; `File.WriteAllBytes(absolutePath, png)`; discard bytes after writing. Fixed resolution and one in flight bound the unavoidable PNG allocation. Keep encode/I/O synchronous initially; any later worker receives only copied managed bytes, never Unity objects.
  9. An **outer `catch (Exception)` covering setup, render, encoding, I/O and cleanup** logs a bounded failure and disables that capture attempt/backoffs; no managed exception escapes into the player loop. In outer `finally`, clear the busy flag through a no-throw cleanup path. Do not retry native-suspect APIs automatically.
  10. Reuse the two owned textures between requests. On shutdown/reconfiguration, restore references, `rt.Release(); UnityEngine.Object.Destroy(rt); UnityEngine.Object.Destroy(pixels);` on the main thread, with each cleanup independently guarded. If choosing per-request textures instead, destroy them in `finally`; never leave native allocations to managed GC.

## 5. Fallback gates, not an API roulette
- Mirror framing insufficient → rank 1 dedicated camera; proven manual render unsupported/blank → support-checked URP request; manual requests unavailable but normal rendering confirmed alive → rank 2. GPU readback stall only → rank 3. UI required → camera-space canvas/stack first.
- If main-thread heartbeat stops, a wall-clock timer cannot run Unity for it. If a newly rendered RT is stale/black, distinguish camera/layer/culling errors from a nonfunctional graphics device; log render-stage completion and pose timestamps, not just file existence. Recreate lost resources once; stop after bounded failure.
- If the player/render thread is suspended or the graphics device is unavailable while locked, **none of the desktop APIs repairs that**. Record capture unavailable; defer to an explicitly unlocked/active-session verification run (or later investigate rank 4 if rendering still runs). Do not unlock, inject hooks, change power settings, build, or run experiments as part of this design task.
